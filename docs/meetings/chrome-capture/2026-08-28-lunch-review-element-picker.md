# chrome-capture 요소 피커 점심시간 자유 리뷰

**날짜:** 2026-08-28
**프로젝트:** chrome-capture (Smart Screenshot Capture) — 클릭으로 요소 선택하는 UX 추가 (목표 버전 v1.1.0)
**참석자:** PM Orca, UX Coral, QA Octopus
**형식:** 점심시간 캐주얼 리뷰 — 정식 스프린트 회의 아님, 결정 사항 아니라 아이디어/우려 자유 발언
**작성:** TS Nautilus

---

> 정식 결정 회의가 아니라서 여기서 나온 얘기가 곧바로 스코프에 반영되는 건 아님. 인상적이었던 것들만 "다음에 고려해볼 것" 섹션에 정리해뒀고, 나머지는 그냥 잡담 기록.

## 대화 요약

**Orca (PM):** 오늘 아침에 올라온 `docs/PRD/chrome-capture-element-picker` 문서 다 봤는데, 원래 목표가 "개발자 아닌 사람도 쓰게 하자"였잖아요. 근데 지금 스펙 보면 Shift+클릭 반복 클라이밍, 레벨별 테두리 두께, 토글 취소... 이거 자체가 좀 파워유저스러운 개념 아닌가 싶어요. 처음 켰을 때 툴바 문구 하나로 이 모든 걸 설명할 수 있나?

**Coral (UX):** 그 생각 저도 했어요. 근데 "그냥 클릭하면 추가되고, 또 클릭하면 취소된다"는 규칙 자체는 되게 직관적이에요. Shift+클릭은 몰라도 상관없는 사람은 그냥 안 쓰면 되고요 — 실수로 텍스트 하나 잘못 클릭해도 "다시 클릭하면 없어진다"만 알면 무서워할 필요가 없어서, 오히려 진입장벽은 낮췄다고 봐요. 다만 테두리 두께로 "몇 단계 올라갔는지" 표현하는 건 저는 좀 약할 것 같아요. 2px, 3px, 4px 차이를 정확히 구분하는 사람이 몇이나 될까... 두께 옆에 작게 숫자 배지("↑2" 같은) 하나 얹는 게 훨씬 명확하지 않을까요.

**Octopus (QA):** 숫자 배지 좋은데요. 저는 다른 쪽이 더 걱정돼요 — `elementFromPoint`랑 `closest()` 쓰는 방식이 Shadow DOM 만나면 어떻게 되는지 스펙에 안 나와 있어서요. 요즘 웹 컴포넌트 쓰는 사이트 꽤 있잖아요. `elementFromPoint`는 open shadow root 안까지 뚫고 들어가는데, `closest()`는 shadow boundary를 못 넘어요. 그러면 호버 동기화(`matchesKnownSelector`)나 피커 자기 자신 판별(`isPickerOwnElement`)이 shadow DOM 안에서는 오작동할 수 있어요.

**Orca:** 그거 심각한 거예요, 아니면 "거의 안 만날 케이스"예요?

**Octopus:** 우리 익스텐션 자체 툴바는 우리가 만드니까 shadow DOM 안 쓰면 그만이라 `isPickerOwnElement`는 문제 없어요. 근데 사용자가 방문한 "임의의 사이트"에 shadow DOM이 있으면 그 안의 요소를 피커로 못 고를 수도 있다는 거죠. 크래시는 안 나요, 그냥 "선택이 안 되거나 이상한 조상이 잡히는" 정도. QA 체크리스트에 "웹 컴포넌트 많이 쓰는 사이트(예: 최신 프레임워크 데모 페이지)에서 한 번 테스트" 항목 추가하면 될 것 같아요. 지금 당장 코드로 대응 안 해도 되고, 알고 넘어가는 정도로.

**Coral:** 그리고 완료 토스트 문구 — "확장 아이콘을 다시 클릭해 캡처하세요" — 이거 아이콘이 브라우저 툴바 어디 있는지 처음 쓰는 사람은 모를 수도 있어요. 화살표로 가리켜줄 수는 없으니 문구로 어떻게든 풀어야 하는데, 지금 문구도 나쁘진 않아요. 크게 안 고쳐도 될 듯.

**Orca:** 호버 동기화 기능(팝업 태그 하이라이트)은 사실 이번 스코프에 왜 들어왔는지 잠깐 헷갈렸어요 — 피커랑 관계없는 기존 수동 입력 목록 개선이잖아요. 근데 다시 보니까 "저장된 요소 재클릭하면 취소된다"는 기능이랑 결이 통해요. 사용자가 태그 이름(`.ad-banner-3` 같은 거)만 보고 그게 화면 어디인지 못 찾으면 취소하기도 어려우니까. 그래서 오히려 두 기능이 서로를 완성해주는 조합이라고 봐요. 굿.

**Octopus:** 하나만 더 — Port 연결 (`chrome.tabs.connect`)이 `chrome://` 같은 특수 페이지에서 실패하는 케이스는 스펙에 try/catch로 조용히 넘어가게 돼 있던데, 그럼 그 페이지에서는 그냥 호버 동기화 기능만 조용히 안 되는 거죠? 에러 토스트 같은 거 안 뜨고?

**Coral:** 그게 맞을 것 같아요 — 애초에 그런 페이지에서는 캡처 자체도 안 되니까(`page-unavailable` 문구 이미 있잖아요), 호버 동기화까지 굳이 별도로 알릴 필요는 없죠.

**Orca:** 좋아요. 스코프 자체는 안 건드리고 싶고, 오늘 나온 것 중에 진짜 챙길 만한 건 두 개인 것 같아요 — 레벨 숫자 배지, 그리고 shadow DOM 테스트 케이스 QA 체크리스트에 추가. 나머지는 구현해보고 다시 얘기하죠.
