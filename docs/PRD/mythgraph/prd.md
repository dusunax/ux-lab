## 1. 제품 개요

### 1-1. 한 줄 정의

**MythGraph는 그리스·로마 신화의 인물, 신, 괴물, 장소, 사건, 사물과 그 관계를 인터랙티브 지식 그래프로 탐색하는 웹 서비스다.**

### 1-2. 배경

그리스·로마 신화는 단일한 연대기나 인물 목록보다 다음과 같은 관계를 중심으로 이해된다.

- 누가 누구의 부모인가
- 누가 누구를 도왔거나 방해했는가
- 어떤 인물이 어느 사건에 참여했는가
- 동일 인물이 그리스명과 로마명으로 어떻게 불리는가
- 하나의 사건이나 인물에 대해 문헌별로 어떤 차이가 존재하는가
- 비슷한 모티프를 가진 신화가 무엇인가

일반적인 위키형 화면은 각 문서의 설명을 읽는 데에는 적합하지만, 여러 문서 사이의 관계와 경로를 한눈에 파악하기 어렵다.

MythGraph는 이러한 정보를 **노드와 관계로 구조화하고 시각적으로 탐색**할 수 있게 한다. 사용자는 특정 인물을 중심으로 주변 관계를 확장하거나, 두 대상의 연결 경로를 찾고, 자연어 의미 검색으로 유사한 인물과 이야기를 발견할 수 있다.

### 1-3. 프로젝트 목적

제품 관점에서는 신화를 관계 중심으로 이해할 수 있는 탐색 경험을 제공한다.

개발 학습 관점에서는 다음 기술을 실제 기능으로 연결한다.

- Graph Database 모델링
- Cypher 기반 관계 탐색
- GraphQL Schema 및 Resolver 설계
- Next.js 서버 경계 설계
- React Flow 기반 그래프 시각화
- Vector Search 및 구조적 탐색 결합
- GraphRAG로 확장 가능한 데이터 구조 설계

## 2. 문제 정의

### 2-1. 사용자 문제

기존 신화 콘텐츠는 주로 문서 단위로 제공되기 때문에 다음 질문에 답하기 어렵다.

- 제우스와 아킬레우스는 어떤 관계 경로로 연결되는가
- 아테나가 도운 영웅과 그들이 물리친 괴물은 누구인가
- 트로이 전쟁에 참여한 신과 인간은 어떻게 연결되는가
- 신의 벌로 영원한 고통을 겪는 인물은 누구인가
- 동일한 가족 관계가 문헌에 따라 어떻게 다르게 설명되는가

사용자는 개별 문서를 여러 개 열고 직접 비교해야 하며, 관계를 머릿속에서 재구성해야 한다.

### 2-2. 제품이 해결할 문제

MythGraph는 다음 방식으로 문제를 해결한다.

1. 신화의 대상을 공통 Entity로 구조화한다.
2. Entity 사이의 관계를 방향성과 속성을 가진 Edge로 저장한다.
3. React Flow에서 관계를 인터랙티브하게 탐색한다.
4. GraphQL을 통해 화면에 필요한 그래프 단위만 조회한다.
5. Neo4j의 경로 탐색으로 N단계 관계 및 최단 경로를 제공한다.
6. Vector Search로 키워드가 정확히 일치하지 않는 의미 기반 질문을 처리한다.
7. 검색 결과를 다시 그래프 관계와 결합해 맥락을 제공한다.

## 3. 목표와 비목표

### 3-1. Goals

#### G-01. Entity 탐색

- 사용자는 이름과 별칭으로 Entity를 검색할 수 있다.
- 사용자는 Entity 유형으로 검색 결과를 필터링할 수 있다.
- 사용자는 Entity 상세 정보와 대표 관계를 확인할 수 있다.

#### G-02. 관계 그래프 탐색

- 선택한 Entity를 중심으로 1단계 관계 그래프를 표시한다.
- 노드를 클릭하여 추가 관계를 동적으로 확장할 수 있다.
- 관계 유형을 필터링할 수 있다.
- 동일 노드와 동일 관계의 중복 렌더링을 방지한다.

#### G-03. 경로 탐색

- 두 Entity 사이의 연결 경로를 조회할 수 있다.
- MVP에서는 제한된 깊이 내의 최단 경로 하나를 반환한다.
- 경로를 React Flow 위에서 강조 표시한다.

#### G-04. 신화 및 사건 탐색

- Entity가 등장하는 Myth와 Event를 조회할 수 있다.
- Myth 또는 Event를 중심으로 참여자와 관련 관계를 그래프로 표시한다.
- Story 단위 설명과 구조적 관계를 함께 제공한다.

#### G-05. 의미 검색

- 사용자는 자연어 문장으로 인물 또는 신화를 검색할 수 있다.
- 검색 결과는 Vector Search 유사도에 따라 정렬한다.
- Entity 유형 등 최소한의 구조 필터를 결합할 수 있다.
- 결과에서 해당 Entity의 관계 그래프로 이동할 수 있다.

#### G-06. 출처 기반 지식 표현

- Entity와 Myth의 설명에 출처 정보를 연결할 수 있다.
- 관계에도 출처 또는 신뢰도 속성을 기록할 수 있다.
- 문헌별 차이를 하나의 사실로 강제 통합하지 않고 별도 관계 또는 주장으로 표현할 수 있는 구조를 마련한다.

#### G-07. 학습 가능한 구현 구조

- Neo4j 연결 정보는 브라우저에 노출하지 않는다.
- Next.js 서버에서 GraphQL API를 제공한다.
- GraphQL Schema, Resolver, Cypher Query, DTO 변환 책임을 분리한다.
- 향후 인증, 관리자 편집, GraphRAG를 추가할 수 있도록 확장 가능한 구조를 사용한다.

### 3-2. Non-Goals

MVP에서 다음은 구현하지 않는다.

- 사용자 로그인 및 회원가입
- 개인 북마크, 즐겨찾기, 탐색 이력
- 일반 사용자 대상 데이터 편집
- 관리자 CRUD 화면
- 실시간 공동 편집
- 커뮤니티 제보 및 검수 워크플로
- 사용자 주석 및 토론 기능 *(향후 추가 예정 없음)*
- 모든 그리스·로마 신화 데이터 수집
- 학술적으로 완전한 문헌 비평 시스템
- 완전한 자연어 질의 → 임의 Cypher 변환
- LLM이 생성한 답변을 사실로 자동 저장
- 다국어 전체 지원
- 모바일 네이티브 애플리케이션
- Neo4j 외 관계형 데이터베이스 병행 운영

## 4. 대상 사용자

### 4-1. 주요 사용자

#### 신화 입문자

- 주요 인물과 관계를 시각적으로 이해하고 싶다.
- 한 인물에서 연관된 이야기로 자연스럽게 이동하고 싶다.

#### 신화 콘텐츠 탐색자

- 특정 모티프나 관계를 기준으로 유사한 이야기를 찾고 싶다.
- 인물·사건·장소가 어떻게 연결되는지 비교하고 싶다.

#### 개발자 및 데이터 학습자

- Graph DB, GraphQL, React Flow, Vector Search가 결합된 실제 구현 사례를 보고 싶다.
- Cypher를 이용한 관계 탐색과 최단 경로를 경험하고 싶다.

### 4-2. 보조 사용자

#### 콘텐츠 관리자

MVP에서는 UI를 제공하지 않지만, seed script 또는 데이터 파일을 통해 다음 작업을 수행한다.

- Entity 추가
- 관계 추가
- Myth 및 Source 추가
- 임베딩 생성
- 데이터 검증

## 5. 핵심 사용자 시나리오

### 시나리오 A. 인물 중심 탐색

1. 사용자가 검색창에 `Athena`를 입력한다.
2. 검색 결과에서 아테나를 선택한다.
3. 아테나를 중심으로 관련 신, 인간, 사건이 표시된다.
4. 사용자가 `HELPED` 관계만 필터링한다.
5. 오디세우스 노드를 클릭해 주변 관계를 확장한다.
6. 오디세우스 상세 패널에서 관련 Myth로 이동한다.

### 시나리오 B. 두 인물 사이 관계 찾기

1. 사용자가 시작 Entity로 `Achilles`를 선택한다.
2. 대상 Entity로 `Zeus`를 선택한다.
3. 서비스가 제한된 깊이 내 최단 경로를 조회한다.
4. 결과 경로만 강조된 그래프를 표시한다.
5. 사용자는 각 Edge의 관계 유형과 근거를 확인한다.

### 시나리오 C. 의미 기반 검색

1. 사용자가 `신의 벌을 받아 끝없는 고통을 겪는 인물`을 검색한다.
2. 검색어 임베딩을 생성한다.
3. Neo4j Vector Index에서 유사 Entity 또는 Knowledge Chunk를 조회한다.
4. 시시포스, 프로메테우스, 탄탈로스 등의 결과를 표시한다.
5. 사용자가 결과 하나를 선택하면 구조적 관계 그래프로 전환한다.

### 시나리오 D. 사건 중심 탐색

1. 사용자가 `Trojan War`를 검색한다.
2. 사건 상세와 주요 참여자를 확인한다.
3. 참여자 유형을 신, 인간, 장소로 필터링한다.
4. 특정 신이 어느 편을 지원했는지 관계를 확인한다.

## 7. 기능 요구사항

### MG-01. Entity 검색

#### 요구사항

- 이름, 그리스명, 로마명, 별칭을 검색 대상으로 한다.
- 부분 일치 또는 Full-text Search를 지원한다.
- Entity 유형 필터를 제공한다.
- 검색 결과는 대표 이름, 유형, 한 줄 설명을 포함한다.
- 검색 결과가 없을 경우 의미 검색으로 전환할 수 있는 진입점을 제공한다.

#### 완료 조건

- 사용자가 이름 또는 별칭으로 Entity를 찾을 수 있다.
- 검색 결과 선택 시 Entity 중심 그래프로 이동한다.

---

### MG-02. Entity 상세

#### 요구사항

- 대표 이름
- 그리스명 또는 로마명
- Entity 유형
- 요약
- 별칭
- 상징 또는 속성
- 직접 연결된 주요 관계
- 관련 Myth
- 출처

#### 완료 조건

- Entity의 핵심 정보와 주변 탐색 진입점을 한 화면에서 확인할 수 있다.

---

### MG-03. 관계 그래프

#### 요구사항

- 초기 조회는 중심 노드와 1단계 관계만 반환한다.
- 사용자는 노드를 선택해 주변 관계를 추가 조회할 수 있다.
- 방향성이 있는 관계는 화살표로 표현한다.
- 관계 라벨을 표시한다.
- Entity 유형과 관계 유형 필터를 지원한다.
- 현재 선택 노드와 탐색 경로를 시각적으로 구분한다.
- 그래프 데이터에는 노드 및 Edge 상한을 적용한다.

#### 완료 조건

- 사용자가 그래프를 확장하며 관계를 탐색할 수 있다.
- 동일 노드가 여러 번 등장하지 않는다.
- 필터 변경 시 현재 그래프에서 조건에 맞는 요소만 표시된다.

---

### MG-04. 최단 경로

#### 요구사항

- 시작 Entity와 대상 Entity를 선택한다.
- 최대 탐색 깊이를 서버에서 제한한다.
- 경로가 존재하면 노드와 관계를 순서대로 반환한다.
- 경로가 없으면 명확한 빈 상태를 표시한다.
- MVP는 최단 경로 하나만 제공한다.

#### 완료 조건

- 서로 연결된 두 Entity 사이의 관계 경로를 시각화할 수 있다.

---

### MG-05. Myth 및 Event 탐색

#### 요구사항

- Myth는 제목, 요약, 주요 출처, 관련 Event를 가진다.
- Event는 참여자, 장소, 선행·후행 관계를 가질 수 있다.
- Myth 또는 Event 중심 그래프를 제공한다.
- 참여 Entity의 역할을 관계 속성으로 표현할 수 있다.

#### 완료 조건

- 사용자가 이야기 단위와 사건 단위를 관계 그래프로 탐색할 수 있다.

---

### MG-06. 의미 검색

#### 요구사항

- 자연어 검색어를 입력받는다.
- 서버에서 임베딩을 생성한다.
- Vector Index를 조회한다.
- 결과에 Entity 또는 Myth 유형 필터를 적용할 수 있다.
- 결과는 제목, 요약, 유형, 유사도 점수를 포함한다.
- 검색 결과 선택 시 구조적 그래프 탐색으로 연결한다.

#### 완료 조건

- 키워드가 일치하지 않아도 의미적으로 관련된 Entity 또는 Myth를 찾을 수 있다.

---

### MG-07. 출처 및 불확실성

#### 요구사항

- Entity, Myth, 관계에 Source를 연결할 수 있다.
- 관계 속성에 confidence 또는 disputed 여부를 기록할 수 있다.
- 상충하는 관계를 삭제하거나 하나로 덮어쓰지 않는다.
- UI에서는 출처가 없는 정보와 출처가 있는 정보를 구분할 수 있다.

#### 완료 조건

- 관계 또는 설명이 어떤 출처에 근거하는지 확인할 수 있다.
- 상충 정보가 존재할 때 이를 사용자에게 숨기지 않는다.

---

### MG-08. Seed 데이터

#### MVP 권장 범위

- Entity 50~80개
- Myth 10~15개
- Event 15~25개
- 관계 150~250개
- Source 5~10개
- Knowledge Chunk 100개 이상

#### 우선 데이터군

- 올림포스 주요 신
- 티탄 신족
- 페르세우스
- 헤라클레스
- 테세우스
- 트로이 전쟁
- 오디세우스
- 주요 괴물과 유물
- 주요 장소

#### 완료 조건

- 모든 핵심 기능을 검증할 수 있을 정도의 연결성과 다양성을 가진 데이터셋이 준비된다.

## 8. UX 원칙

### 8-1. 그래프는 설명을 대체하지 않는다

그래프는 관계를 이해하는 도구이며, Entity와 Myth에 대한 설명은 상세 패널에서 함께 제공한다.

### 8-2. 한 번에 모든 관계를 표시하지 않는다

초기 그래프는 작게 시작하고 사용자의 선택에 따라 확장한다.

### 8-3. 관계 유형을 읽을 수 있어야 한다

색상만으로 관계를 구분하지 않고 라벨, 방향, 상세 정보를 함께 제공한다.

### 8-4. 현재 탐색 맥락을 유지한다

사용자가 노드를 확장하거나 상세를 열어도 기존 탐색 그래프가 불필요하게 초기화되지 않는다.

### 8-5. 신화의 불확실성을 숨기지 않는다

출처 차이와 상충 관계를 오류로 취급하지 않고 데이터의 특성으로 표현한다.

## 9. 성공 지표

MVP에서는 대규모 사용자 지표보다 기능 완성도와 탐색 가능성을 중심으로 평가한다.

### 제품 지표

- 검색 후 Entity 상세 도달 성공률
- 그래프 노드 확장 성공률
- 최단 경로 조회 성공률
- 의미 검색 결과 선택률
- 빈 결과 발생률
- 그래프 API 오류율

### 기술 지표

- 초기 그래프 API 응답 시간
- 노드 확장 API 응답 시간
- 최단 경로 조회 시간
- Vector Search 응답 시간
- GraphQL 오류율
- Neo4j 세션 누수 여부
- 브라우저 번들 내 Neo4j 자격 증명 미포함 여부

### MVP 목표값

| 항목 | 목표 |
| --- | --- |
| 초기 그래프 응답 | 일반적인 조회에서 2초 이내 |
| 노드 확장 | 일반적인 조회에서 1.5초 이내 |
| 검색 결과 | 일반적인 검색에서 1초 이내 |
| 최단 경로 | 제한 깊이 내 일반적인 조회에서 2초 이내 |
| 그래프 렌더 노드 | 기본 100개 이하 |
| 그래프 렌더 관계 | 기본 200개 이하 |

목표값은 초기 데이터셋과 무료 인프라를 기준으로 한 제품 목표이며, 실제 측정 후 조정한다.

## 11. 리스크

| 리스크 | 영향 | 완화 |
| --- | --- | --- |
| 그래프가 지나치게 복잡해짐 | 가독성 저하, 렌더 성능 저하 | 초기 1단계 조회, 노드·Edge 제한, 필터, 점진적 확장 |
| 관계 유형이 과도하게 증가 | 스키마 일관성 저하 | 관계 사전 정의, 유사 관계 통합, seed validation |
| 문헌별 정보 충돌 | 잘못된 단일 사실 표현 | Source 및 Claim 구조, disputed 속성 |
| 자동 GraphQL에 과도하게 의존 | Resolver 학습 목표 약화 | 핵심 도메인 Query는 직접 Resolver와 Cypher 작성 |
| 무료 인프라 제한 | 응답 지연, 일시 중지 | 작은 데이터셋, 쿼리 제한, 캐시, 연결 재사용 |
| 임베딩 비용 또는 호출 제한 | 의미 검색 불안정 | 초기 데이터는 오프라인 생성, 검색어만 온라인 생성 |
| 임의 길이 경로 조회 | 비용 급증 | maxDepth, maxNodes, timeout, 허용 관계 제한 |
| 데이터 품질 부족 | 검색 및 관계 결과 신뢰 저하 | 검증 스크립트, Source 필수화, 중복 검사 |

## 12. 오픈 이슈

- Entity를 하나의 공통 라벨과 보조 라벨로 구성할지, 유형별 최상위 라벨로 분리할지
- Myth와 Event를 별도 노드로 유지할지, 일부 단순 사건을 관계 속성으로 둘지
- Source와 Claim을 MVP부터 분리할지
- 의미 검색 대상을 Entity 설명으로 할지, Knowledge Chunk로 분리할지
- 임베딩 공급자를 무엇으로 선택할지
- Full-text Search와 Vector Search의 랭킹을 어떻게 결합할지
- React Flow 자동 레이아웃 엔진으로 무엇을 사용할지
- 초기 데이터의 기준 문헌과 번역 표기를 어떻게 정할지
